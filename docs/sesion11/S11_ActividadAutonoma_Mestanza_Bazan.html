1. Introducción y Objetivos

En el ámbito de las aplicaciones móviles clínicas y farmacéuticas críticas, la disponibilidad continua del sistema frente a interrupciones o ausencia total de conectividad a internet resulta fundamental para evitar paradas operativas en el despacho de medicamentos y consulta de inventarios. La arquitectura Offline-First (fuente única de verdad local) garantiza que la aplicación sea plenamente funcional sin red, utilizando una base de datos local embebida como intermediaria reactiva obligatoria ante la interfaz de usuario.

El presente informe documenta la implementación completa y validación empírica de la Sesión 11 en el proyecto PharmaMobil (Kotlin Multiplatform con Compose Multiplatform), persistiendo el catálogo de productos en SQLite mediante SQLDelight 2.1.0 y sincronizándolo de forma bidireccional y transaccional con el backend PharmaSoft (Spring Boot 3 + PostgreSQL/H2).

Nota de Alcance Multiplataforma (KMP):
En cumplimiento de los lineamientos de arquitectura limpia en KMP, se configuran e implementan los creadores de driver nativos tanto para Android (CreadorDeDriverAndroid con AndroidSqliteDriver) como para iOS (CreadorDeDriverIos con NativeSqliteDriver), manteniendo la coherencia de compilación multiplataforma. Conforme a las pautas y autorización expresa del docente, la ejecución, pruebas instrumentales y capturas de evidencia se realizan sobre el entorno Android (emulador Google Pixel 8, API 34).

Objetivos Técnicos Específicos

  • Definición del Esquema Relacional con SQLDelight: Diseñar y compilar el archivo Producto.sq con 8 columnas normalizadas (incluyendo la bandera de control pendiente INTEGER) y consultas reactivas automáticas.
  • Eliminación de la Carga Imperativa REST: Erradicar el patrón de recarga directa en memoria (ListarProductosUseCase y cargarProductos()) para que la vista consuma exclusivamente el Flow<List<Producto>> emitido por SQLite.
  • Generación Atómica de Identificadores Negativos: Implementar en SQLite un generador de claves primarias temporales locales (-1, -2, ...) para altas offline sin colisionar con las secuencias del backend.
  • Reemplazo Transaccional y Sincronización Remota: Crear el mecanismo atómico de reconciliación que envía pendientes al servidor y sustituye la clave negativa por el identificador permanente positivo remoto dentro de una transacción local.
  • Resiliencia de Red y Exclusión Mutua: Proteger el repositorio con Mutex para prevenir condiciones de carrera y propagar errores tipados de red (ErrorApiException) sin corromper el caché ni falsear la hora de sincronización.

2. Arquitectura de Datos y SQLDelight

2.1 Esquema Relacional (Producto.sq)

El contrato de persistencia se definió en el módulo compartido shared/src/commonMain/sqldelight/pe/edu/upeu/pharmamobil/db/Producto.sq. Cada producto se almacena con tipos nativos de SQLite mapeados a Kotlin: 

CREATE TABLE producto (
    id INTEGER NOT NULL PRIMARY KEY,
    nombre TEXT NOT NULL,
    precio REAL NOT NULL,
    stock INTEGER NOT NULL,
    activo INTEGER NOT NULL DEFAULT 1,
    imagen TEXT NOT NULL DEFAULT '',
    categoria TEXT NOT NULL DEFAULT '',
    pendiente INTEGER NOT NULL DEFAULT 0
);

-- Consultas Reactivas y Operaciones Atómicas
todos:
SELECT id, nombre, precio, stock, activo, imagen, categoria, pendiente
FROM producto
ORDER BY id ASC;

pendientes:
SELECT id, nombre, precio, stock, activo, imagen, categoria, pendiente
FROM producto
WHERE pendiente = 1
ORDER BY id ASC;

siguienteIdTemporal:
SELECT COALESCE(MIN(id), 0) - 1
FROM producto
WHERE id < 0;

insertarOActualizar:
INSERT OR REPLACE INTO producto(id, nombre, precio, stock, activo, imagen, categoria, pendiente)
VALUES (?, ?, ?, ?, ?, ?, ?, ?);

reemplazarIdTemporal:
UPDATE producto
SET id = :nuevoId, pendiente = 0
WHERE id = :idTemporal;

eliminarPorId:
DELETE FROM producto WHERE id = :id;

4. Análisis Comparativo: Modelo REST Directo vs. Offline-First

Dimensión Modelo Anterior (REST Directo - Sesión 8/10) Modelo Actual (Offline-First Reactivo - Sesión 11)
Fuente de Verdad Memoria volátil (List<Producto> en ViewModel) recargada vía HTTP. Base de datos local SQLite física gestionada por SQLDelight.
Disponibilidad sin Red Nula. La pantalla muestra spinner infinito o pantalla de error 500/SinConexion. Total. Los datos locales se cargan en milisegundos desde caché.
Alta de Nuevos Datos Bloqueada si no hay red o si el servidor no responde. Permitida. Se genera ID negativo temporal y se marca pendiente.
Actualización de la Vista Imperativa mediante llamadas manuales a cargarProductos(). Reactiva continua mediante Flow<List<Producto>> desde SQLite.
Integridad Transaccional Dependiente de la estabilidad de la conexión remota durante la llamada. Garantizada por transacciones ACID en SQLite y exclusión mutua con Mutex.

5. Conclusiones y Lecciones Aprendidas

  1. Independencia Operativa y Resiliencia: La transición a una arquitectura Offline-First transformó la aplicación móvil en un sistema tolerante a fallos, capaz de operar en áreas hospitalarias con baja cobertura o modo avión sin degradar la experiencia de usuario.
  2. Desacoplamiento Reactivo mediante Flow: Eliminar la carga manual imperativa (ListarProductosUseCase y cargarProductos()) garantizó que la interfaz reaccione únicamente a las mutaciones registradas en SQLite, evitando discrepancias de estado entre la base local y la memoria del ViewModel.
  3. Estrategia Segura de Identificadores Temporales: La asignación de números negativos correlativos (-1, -2, ...) en SQLite previene colisiones con las secuencias autoincrementales del backend Spring Boot, permitiendo una sustitución atómica limpia una vez restablecida la red.
  4. Multiplataforma Coherente en KMP: La integración de SQLDelight con drivers específicos por plataforma (CreadorDeDriverAndroid y CreadorDeDriverIos) consolida un núcleo de lógica de datos 100% compartido en commonMain, listo para su despliegue tanto en Android como en iOS.
